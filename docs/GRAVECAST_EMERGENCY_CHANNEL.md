# Gravecast: Emergency Channel

> A lightweight emergency app that works when normal apps fail.

We are building a modern PWA that uses Gopher for info, IRC for chat, and Web Radio for broadcast, so people can get help even when the internet is almost dead.

Status: planned. Work starts next session.

## Targets

- Works on 2G
- Works at 5% battery
- No Play Store
- No account
- Total size under 1 MB

## One app, three tabs

### 1. Board (Gopher-style info)

Text-only information: shelters, helplines, updates.

- Loads in about 1 second on 2G.
- A tiny Node server on Render serves the content as plain text files.
- The frontend fetches them and displays them.

### 2. Chat (IRC-style)

- No login. Use a phone number or OTP, then pick a nickname.
- First version: embed the KiwiIRC web client and auto-join `#emergency`.
- Later: self-host an IRC server with Ergo, which needs about 30 MB of RAM.

### 3. Radio (shortwave-style web radio)

- Streams public radio (AIR / KiwiSDR) in the browser.
- A tuning dial, with static noise generated by the Web Audio API.
- Later: anyone can broadcast from their mic over WebRTC.

## App shell

A PWA: Next.js or plain HTML, plus `manifest.json` and a service worker.

- Can be added to the home screen.
- Works offline after the first load.

## Open questions for tomorrow

These are concerns to check before we build. None of them are verified yet.

1. **Render cold starts.** Render's free web services sleep after about 15 minutes idle, and the first request after that is slow. That is risky for an emergency app. Options: pre-render the Board into static files on Vercel, use a keep-alive ping, or pick a host that doesn't sleep.
2. **No raw TCP on Render.** Render only exposes HTTP and WebSocket, so classic Gopher (port 70) and IRC (port 6667) won't work there directly. The Board can serve "Gopher-style" text over HTTP. IRC needs a WebSocket transport; Ergo supports WebSocket listeners.
3. **The 1 MB budget versus KiwiIRC.** The KiwiIRC client is likely larger than the whole budget. A small custom IRC-over-WebSocket client might fit better. Measure it first.
4. **OTP versus "no account".** Phone OTP needs an SMS provider, costs money, and works poorly when the network is failing. Decide whether this is nickname-only, with optional verification later.
5. **Moderation on `#emergency`.** Spam, misinformation, and abuse. We need rate limits, operators, and a way to pin verified updates.
6. **Radio sources.** Check whether AIR and KiwiSDR streams allow embedding (CORS, permission, usage limits). On 2G we need a low bitrate stream, such as Opus at about 16–24 kbps.
7. **WebRTC broadcasting.** Sending one mic to many listeners needs a TURN server and an SFU, which goes beyond a free tier.
8. **What "offline" really means.** The service worker can cache the shell and the last Board snapshot. Chat and Radio still need some connection. Show a clear "last updated" time on the Board.
9. **Battery.** Keep wake-ups, polling, and audio decoding to a minimum. Prefer server push or long intervals over frequent polling.
10. **Where it lives in the monorepo.** For example `apps/gravecast` (PWA) and `apps/board-server` (Node), and whether to reuse `groove-ui` given the 1 MB budget (probably only tokens and a few small pieces).
